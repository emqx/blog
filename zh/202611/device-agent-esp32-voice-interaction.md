从语音终端到桌面助手，ESP32 正被用于越来越多的智能硬件项目。围绕开发者熟悉的音频、显示与传感器能力，EMQ 通过 **Device Agent** 探索了一条从硬件接入到智能体应用的开发路径。本文以共享仪器室为例，介绍**如何用 ESP32 终端完成使用状态标识、仪器移动记录查询和环境照度读取，并通过语音与屏幕反馈结果。**

## **ESP32：从硬件能力到智能交互**



ESP32 家族覆盖了多种联网与嵌入式应用需求。经典 ESP32 拥有丰富的开发生态：

- **ESP32-C3** 适用于传感器、开关等联网终端；
- **ESP32-C6** 提供 Wi-Fi 6、蓝牙 LE 和 IEEE 802.15.4 连接能力；
- **ESP32-S3** 具备双核处理器、向量指令与丰富外设接口，可用于音频、显示和智能交互开发；
- **ESP32-P4** 面向更高性能的人机交互与多媒体应用，无线连接需搭配相应方案。

对于开发者而言，这些芯片与开发板已经提供了丰富的硬件基础。麦克风可以采集声音，扬声器可以播放音频，屏幕可以显示信息，传感器能够感知环境。随着大语言模型与智能体应用的发展，开发重点也进一步延伸：**如何让用户通过自然语言调用这些能力，并根据设备的实际状态完成任务？**

本文的演示以 ESP32-S3 开发板为基础，将语音输入输出、屏幕显示与传感器数据连接到 Device Agent。ESP32 负责本地采集和执行，部署在电脑或服务器等环境中的 Device Agent 服务负责理解请求、读取设备数据并调用相应操作，共同完成从用户表达、平台状态到实际硬件动作的连接。

## Device Agent：让设备能力进入智能体应用



为一台设备增加智能交互，需要让智能体理解它能执行哪些操作、提供哪些数据，以及操作完成后如何确认结果。Device Agent 将这些信息组织为设备模型，通过属性、命令和事件描述硬件能力，为自然语言交互与真实设备之间建立明确的调用依据。

开发者可以用自然语言描述设备，生成并确认模型，再通过 MQTT 或 SDK 接入硬件；也可以先利用模拟器验证交互。当用户提出请求时，智能体根据设备模型选择操作、组织参数，并结合设备返回的结果和上报的数据进行反馈。已有 IoT 平台的设备，则可以通过适配后的平台接口接入，复用原有物模型与设备数据。

这使开发者能够在已有硬件项目上逐步增加智能体能力：采集、控制与屏幕刷新继续由固件完成，设备模型为这些功能提供统一的语义描述，减少在不同交互入口中重复定义设备能力的工作。

## 实战场景：共享仪器室状态管理



下面我们以共享仪器室为例，展示上述能力如何落到具体的日常使用场景中。

实验室中的共享仪器通常由不同人员轮流使用。以一间放置共享仪器的独立房间为例：

- 使用者开始操作时，需要告知其他人房间正在使用；
- 结束后，需恢复空闲标识。
- 再次使用前，工作人员还可能需要确认仪器近期是否发生移动，并查看室内照明情况。

围绕这些日常操作，ESP32 终端可以连接门口状态屏、使用指示灯、位移传感器和照度传感器，通过麦克风接收请求，再用屏幕和扬声器反馈结果。

### 使用状态标识



开始使用仪器时，操作人员可以发出语音指令：

> *把门口屏幕改成「使用中」，并点亮使用指示灯。*

Device Agent 调用对应的属性设置能力，ESP32 刷新屏幕并控制指示灯，完成后返回结果。

同样，使用结束后，再通过语音将屏幕改为「空闲」并关闭指示灯。这里的状态由使用者主动设置，用于向其他人传达房间的使用情况。

### 使用前检查



**仪器移动记录**服务于使用前的核查。例如，工作人员可以询问：

> *过去一小时有没有检测到仪器移动？*

系统查询该时间范围内上报的位移事件，返回记录情况，供工作人员进一步检查位置、接线或安装状态。位移事件提供的是移动线索，是否需要重新校准或维护，仍由人员结合仪器要求判断。

**照度数据**可以作为另一项使用前检查信息。用户可以要求：

> *读一下当前照度，低于设定阈值就播放一次提示音。*

系统读取当前数据，根据预先配置的阈值决定是否调用提示音命令。这是一次主动发起的检查，与仪器使用标识、移动记录查询分别对应具体需求。

## **定义设备能力，创建智能体**



要让上述操作进入对话，需要先在开发阶段定义终端能力。开发者可在 Device Agent 的创建设备智能体入口输入提示词：

> *创建一个实验室仪器终端，支持控制指示灯、修改门口屏文字、播放一次提示音，并上报仪器位移事件和房间照度，供用户查询和语音控制。*

这段提示词用于让 Device Agent 生成设备模型，说明终端具备哪些能力。开发者据此检查生成的属性、命令和事件，确认与硬件实现一致后，再创建设备智能体并接入 ESP32。前文的「把门口屏改成使用中」等语句，则是终端接入后使用者向设备智能体发出的日常操作请求。

![image.png](https://assets.emqx.com/images/45fd12ef4cb0fb52274eb06f55b9fdbd.png)

在本次采用 IoT 平台集成的演示中，指示灯与门口屏文字对应可写属性，照度作为传感器数据上报，仪器移动对应位移事件，播放提示音则作为可调用命令。设备模型为这些能力提供统一定义，使后续的语音请求能够对应到明确的数据查询与硬件操作。

## **打通 ESP32 硬件接入链路**



模型确认后，开发者导出 MQTT 接入代码，将其适配到 ESP32 固件，并与已有驱动对接。

- 收到**指示灯属性**更新时，固件调用 GPIO 控制逻辑；
- 收到**显示文字**更新时，调用屏幕驱动刷新内容；
- 收到**提示音命令**时，调用相应音频输出逻辑。
- 传感器采集的**照度**与检测到**位移**事件，通过 MQTT 上报。

屏幕由此成为智能体向现场呈现信息的出口。用户说「把门口屏改成使用中」，智能体通过设备模型发起属性更新，ESP32 将文字写到屏幕，并返回执行结果、上报实际状态。原有驱动得以复用，新增的接入逻辑负责将设备消息与硬件操作连接起来。

麦克风与扬声器通过语音链路接入。本次演示采用按键对讲，按住开始录音，松开结束。ESP32 将麦克风采集的音频整理为 16 kHz、单声道、16 bit PCM，通过 WebSocket 发送给语音服务，识别结果进入 Device Agent 会话；生成的语音回复再返回终端，由扬声器播放。

![image.png](https://assets.emqx.com/images/48300cd80d3b60692f3a8836018c75b0.png)

整个演示使用两条相互配合的连接：WebSocket 承载语音收发与会话控制，MQTT 承载设备数据与控制消息。Device Agent 通过已适配的 IoT 平台接口查询数据、执行操作，两条链路关联同一台设备。语音请求涉及改灯、改屏幕或播放提示音时，仍然调用前面已经接好的设备能力。

对已有 ESP32 项目而言，可以先完成设备上线、状态上报和文字控制，确认硬件动作与返回结果一致，再接入语音。这样既方便定位驱动、连接与交互中的问题，也能逐步验证从麦克风输入到设备执行、扬声器反馈的完整过程。

## **从 Demo 到更多智能硬件应用**



当硬件能力被组织成智能体能够理解和调用的接口后，同一组功能就可以支持更多交互表达与任务组合。用户可以单独查询照度，也可以要求修改屏幕文字，或把查询与控制放进一次对话。只要已经实现的设备能力和接口保持不变，调整表达方式或重新组合已有操作，通常无需为此修改固件。

这些交互始终以实际设备数据为依据。例如查询仪器移动记录时，需要明确查询时间范围；只有确认数据链路与记录完整，才能将未查到事件表述为该时段内未检测到移动。照度检查则使用预先配置的阈值，确保判断条件清晰、结果可核对。

同样的开发方式可以延伸到更多项目：

- 为桌面助手接入温湿度传感器，让用户通过语音了解环境；
- 为智能面板增加自然语言控制入口，调用灯光、继电器与显示能力；
- 为设备状态终端接入运行数据和异常事件，让使用者更方便地查询设备情况；
- ……

对于 ESP32 开发者，可以从一个已经跑通的硬件项目开始，选取一个可查询的状态、一个可执行的动作和一个可上报的事件，用 Device Agent 建立模型并验证交互，再逐步接入麦克风、扬声器和屏幕。熟悉的外设与固件，由此成为开发智能体应用的起点。
